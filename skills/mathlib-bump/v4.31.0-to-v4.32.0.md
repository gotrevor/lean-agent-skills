# mathlib v4.31.0 → v4.32.0 — breaking-change cookbook (provisional)

This is a **seed draft**, started 2026-07-20 from the official Lean 4.32 release notes,
Mathlib's own v4.32.0-rc1 port, and public downstream upgrade commits. One fleet port has landed
(lean-gallery — see the ledger at the end); most entries are still un-reproduced locally, so it
deliberately distinguishes four kinds of evidence:

- **Lean release note** — an upstream-declared breaking change and migration, not necessarily hit
  in a downstream project yet.
- **Mathlib port** — a concrete source change in Mathlib's v4.32.0-rc1 bump commit.
- **Downstream port** — a concrete source change in a public project's v4.31 → v4.32 bump.
- **Fleet port** — hit in one of *our* v4.31 → v4.32 ports, with the exact error text. These are the
  only entries held to the same empirical standard as the mature v4.29.1 → v4.31.0 catalog.

Unlike [`v4.29.1-to-v4.31.0.md`](v4.29.1-to-v4.31.0.md), this file is not yet a fully
empirical symptom catalog. Promote and sharpen entries as the fleet port reproduces them; delete
watch items that never occur.

## First-response checklist

1. Pin the pair exactly: `leanprover/lean4:v4.32.0` and Mathlib `v4.32.0`.
2. Regenerate `lake-manifest.json`, fetch the matching cache, then run a full `lake build` — of
   **every configured library**, not just `defaultTargets` (see Part 4).
3. Re-pin the **satellites**: the version is recorded outside the three lockstep files too, and
   `lake build` reads none of them. Part 4 has the checklist.
4. If an error is inside `do` notation, temporarily scope
   `set_option backward.do.legacy true in` over the smallest declaration. If that alone makes it
   compile, the new elaborator is the cause; use the migrations in Part 1 rather than leaving a
   project-wide compatibility switch without comment.
5. For proof failures, insert `trace_state` and build one file with
   `lake env lean Path/To/File.lean`; gate the result with the real target or full `lake build`.
6. Compare `#print axioms` for headline theorems against the v4.31 baseline. Green still does not
   imply faithful.

# Part 1 — Lean 4.32 language and tool changes

## A. The new `do` elaborator is now the default

**Evidence:** Lean release note; Mathlib port; downstream port.

Lean 4.32 flips `backward.do.legacy` to `false`. The compatibility switch is the fastest diagnostic:

```lean
set_option backward.do.legacy true in
def suspectDefinition := do
  ...
```

One downstream `ResultProp` port used this switch to get the project green. That is a useful bisect
and, when a true rewrite is disproportionately risky, a defensible temporary bridge. Prefer a local
scope and leave an issue/TODO; a file- or project-wide setting hides which declarations still depend
on legacy control flow.

### Nested `return` now means early return

Inside a nested action such as `(← do ...)` or `(← try ... catch ...)`, `return e` now returns from
the **enclosing** `do`, not merely from the nested action. This can be a silent behavior change, not
just an elaboration error. Under v4.32, `nestedReturn true` below evaluates to `5`, skipping the
`+ 100`:

```lean
def nestedReturn (stop : Bool) : Id Nat := do
  let x := (← do
    if stop then return 5
    pure 7)
  pure (x + 100)
```

If the intent is to produce the nested action's value, make its value branches use `pure`:

```lean
let x := (← do
  if stop then pure 5 else pure 7)
```

The other official migration is to add a boundary around the inner block: `(← (do ...))`; that
preserves the old inner early-return interpretation. Mathlib's own port contains many mechanical
`return none` → `pure none` and `return some ...` → `pure <| some ...` changes where the `return`
was already at a terminal branch.

### Refutable `let` patterns may need an explicit outer `match`

Dependent meta code was especially sensitive. Mathlib repeatedly changed this shape:

```lean
-- v4.31 shape
meta def extension : Result := do
  let some p := p? | pure .none
  ... p ...

-- v4.32 shape
meta def extension : Result :=
  match p? with
  | none => pure .none
  | some p => do
    ... p ...
```

This is worth trying when the result type depends on the matched value (common with `Qq`) or the
new elaborator reports a mismatch around the fallback branch. The explicit match makes the branch
boundary and dependent refinement unambiguous.

## B. `do match` arms are non-dependent by default

**Evidence:** Lean release note; Mathlib port.

If a branch refines an indexed family and later terms depend on that refinement, a formerly valid
match can fail with a type mismatch or inaccessible-motive error. Restore dependent matching
explicitly:

```lean
match (dependent := true) value with
| .zero => ...
| .succ n => ...
```

Mathlib's RC port added `(dependent := true)` throughout its quoted-expression and positivity/ring
meta code. A second robust shape is to destructure the indexed value **outside** `do`:

```lean
def f (x : Indexed a) : MetaM ... :=
  match x with
  | .mk b h => do
    ...
```

Do not add dependent matches indiscriminately: they constrain the motive and can make ordinary code
harder to elaborate. Use them where a constructor changes the types available in the branch.

## C. `do` now requires `Pure`, not only `Bind`

**Evidence:** Lean release note; fleet watch item.

A custom effect type with only `Bind` can now fail as soon as it uses `do` notation because the new
elaborator requires a `Pure` instance. Add a lawful `Pure` instance if the abstraction really has one.
If it does not, spell the composition with `bind` rather than inventing a mathematically false
`pure` operation. This has not yet been observed in the local fleet.

## D. Nested-action parser code may need both a rename and a syntax-kind annotation

**Evidence:** Lean release note; downstream port.

Lean renamed the parser/API term `liftMethod` to `nestedAction` and removed the temporary
`Lean.Parser.Term.liftMethod` alias. Code that names the parser constant must use
`Lean.Parser.Term.nestedAction`.

Custom syntax walkers matching the `← term` form may also need to pin the antiquotation kind after
nested actions were broadened to arbitrary `doElem`s:

```lean
-- before
| `(← $e) => ...

-- after
| `(← $e:term) => ...
```

This exact change appeared in a downstream tactic extension during its v4.32 bump.

## E. `Std.Time.DateTime` was redesigned

**Evidence:** Lean release note; downstream port.

The old timezone-indexed `DateTime (tz : TimeZone)` was removed, and the former
`ZonedDateTime` became the new `DateTime`. A direct downstream replacement for timestamped logging
was:

```lean
-- before
let t ← Std.Time.DateTime.now (tz := Std.Time.TimeZone.GMT)

-- after
let tm ← Std.Time.Timestamp.now
let t := Std.Time.DateTime.ofTimestampWithZone tm Std.Time.TimeZone.GMT
```

Also rename direct uses of the old `ZonedDateTime` type to `DateTime`.

## F. Lake lint selection is option-based

**Evidence:** Lean release note; Mathlib/downstream ports.

The old `lake lint --extra`, `lake lint --lint-all`, and `@[builtin_nolint]` interfaces are removed.
Select linter options explicitly:

```bash
lake lint --linters=linter.extra
lake lint --linters=linter.checkUnivs,-linter.deprecated
lake lint --lint-only=linter.checkUnivs
```

Per-declaration suppression now uses the corresponding option:

```lean
set_option linter.checkUnivs false in
structure IntentionallySeparateUniverses where
  ...
```

Mathlib's port removed `@[nolint checkUnivs]`; downstream projects made the same
`@[nolint checkUnivs]` → `set_option linter.checkUnivs false in` migration. Prefer fixing a warning
when the declaration is genuinely wrong; retain a scoped option with a comment when the separate
universes are intentional.

The Mathlib tag also exposes `linter.defProp`: a `def` whose inferred type is `Prop` is usually better
spelled as a `theorem`/`lemma`. If the definition is intentionally data-like API whose value happens
to be a proposition, suppress it locally:

```lean
set_option linter.defProp false in
noncomputable def canonicalStatement := someTheorem specializedArguments
```

This is mostly a lint/CI failure rather than an elaboration failure.

# Part 2 — Mathlib v4.32 API changes

## G. `[NoAtoms μ]` must become `[NullSingletonClass μ]`

**Evidence:** Mathlib change; multiple downstream ports.

Mathlib renamed the class and related declarations:

```lean
-- before
import Mathlib.MeasureTheory.Measure.Typeclasses.NoAtoms
variable [NoAtoms μ]
haveI : NoAtoms (gaussianReal 0 1) := noAtoms_gaussianReal one_ne_zero

-- after
import Mathlib.MeasureTheory.Measure.Typeclasses.NullSingletonClass
variable [NullSingletonClass μ]
haveI : NullSingletonClass (gaussianReal 0 1) :=
  nullSingletonClass_gaussianReal one_ne_zero
```

There is a deprecated term alias `NoAtoms := NullSingletonClass`, but it is not itself registered as
a class. Consequently, term-level old names may merely warn while `[NoAtoms μ]`, `haveI : NoAtoms μ`,
and instance search hard-fail. This alias gap is why a global textual migration is safer than fixing
only the first error.

Search both types and derived names:

```bash
rg 'NoAtoms|noAtoms' --glob '*.lean'
```

Typical lower-camel names changed in parallel (`noAtoms_gaussianReal` →
`nullSingletonClass_gaussianReal`, `pi_noAtoms` → `pi_nullSingletonClass`). Let deprecation messages
identify the rest.

## H. Eta-expanded continuity/measurability combinators acquired `fun_` names

**Evidence:** Mathlib change; downstream port.

Mathlib restated families such as `Continuous.neg` in point-free form and generated the eta-expanded
forms with `@[to_fun]`. Choose the lemma that matches the expression's head:

```lean
-- point-free function operation: `-f`, `f - g`, `f * g`
hf.neg
hf.sub hg
hf.mul hg

-- eta-expanded operation: `fun x => -f x`, `fun x => f x - g x`, ...
hf.fun_neg
hf.fun_sub hg
hf.fun_mul hg
hf.fun_pow n
hf.fun_smul hg
```

This affects `Continuous`, `ContinuousOn`, `ContinuousAt`, `ContDiff`, `Measurable`, and related
families. A common symptom is that `.neg`/`.sub` still resolves, but its result is point-free while
the expected function is eta-expanded (or the reverse), leaving a type mismatch that looks
definitionally trivial. Read the expected function, then choose `op` versus `fun_op`; do not stack
unrelated `simp` lemmas around the mismatch.

## I. `AffineSubspace.smul_vsub_vadd_mem` is now a lemma, not the structure field

**Evidence:** Mathlib change; downstream port.

Term-level calls retain the pleasant unprimed theorem, but structure construction must use the real
field name:

```lean
noncomputable def xAxis : AffineSubspace ℝ P where
  carrier := ...
  smul_vsub_vadd_mem' c p₁ p₂ p₃ hp₁ hp₂ hp₃ := by
    ...
```

If a `where` block says `'smul_vsub_vadd_mem' is not a field` / reports the primed field missing,
add the prime only at the constructor site. Existing proof calls such as
`s.smul_vsub_vadd_mem c hp₁ hp₂ hp₃` remain unprimed.

## J. Pointwise `gcongr`/`grw` obligations may be discharged or require an explicit weakening

**Evidence:** downstream ports; provisional behavior entry.

Two small patterns recurred in real upgrade commits:

1. `gcongr` now sometimes closes a monotonicity side goal that an immediately following `exact ...`
   used to solve. The stale `exact` then errors because there are no goals. Delete only the closer
   that `trace_state` confirms is redundant.
2. `grw [h]` may reject `h : a < b` when the monotonicity step needs `a ≤ b`. Supply the weakening:

   ```lean
   grw [h.le]
   ```

These are observed downstream but have not yet been bisected to a single Mathlib PR. Keep this entry
provisional until the fleet produces stable symptoms and exact error text.

## K. `Northcott.comp_of_finite_fibers` now consumes `TendstoCofinite`

**Evidence:** Mathlib change; downstream port.

Passing a finite-singleton-preimage proof directly can now type-mismatch. Build the stronger packaged
statement first:

```lean
letI : Filter.TendstoCofinite f :=
  (Filter.tendstoCofinite_iff_finite_preimage_singleton f).mpr finite_preimage
exact Northcott.comp_of_finite_fibers
```

This is a narrow number-theory API change, included because its old theorem name survived while its
argument contract changed — exactly the sort of bump failure that a name search does not explain.

## L. Smaller hard rename seen in downstream ports

**Evidence:** Mathlib/downstream port. This is easy once identified:

- `intervalIntegral.intervalIntegrable_const` → `_root_.intervalIntegrable_const`.

## M. `HasSubset.Subset.eventuallyLE` → `LE.le.eventuallyLE`

**Evidence:** Fleet port (lean-gallery). The exact message:

```
error: LeanGallery/NumberTheory/Erdos482/General/DoublingOrbit.lean:59:37:
  `HasSubset.Subset.eventuallyLE` has been deprecated: Use `LE.le.eventuallyLE` instead

Note: The updated constant is in a different namespace. Dot notation may need to be changed
(e.g., from `x.eventuallyLE` to `LE.le.eventuallyLE x`).
```

In v4.31 this was the real theorem; in v4.32 it is a deprecated alias (`since := "2026-03-16"`,
`Mathlib/Order/Filter/Basic.lean`), so the deprecation lands squarely inside this bump window.
The **signature is unchanged** — it still takes `h : s ⊆ t` — so the fix is only the name:

```lean
-- before
have hle : T ⁻¹' A ≤ᵐ[volume] A := HasSubset.Subset.eventuallyLE hpre
-- after
have hle : T ⁻¹' A ≤ᵐ[volume] A := LE.le.eventuallyLE hpre
```

Note what the appended hint is warning about: the namespace moved from `HasSubset.Subset` to
`LE.le`, so a *dot-notation* call site (`hpre.eventuallyLE`) does **not** survive the rename — the
hypothesis is spelled `⊆`, which elaborates to `HasSubset.Subset`, not `LE.le`. Prefixed call sites
like the one above are a pure textual swap; dot-notation ones need un-dotting.

# Part 3 — Watch items not yet reproduced in the fleet

Keep these in mind, but do not cargo-cult edits merely because they appear in the release notes:

- `try`/`catch` no longer accepts a body whose result reaches the surrounding expected type only
  through a coercion. Make the coerced result explicit at the branch.
- In `grind`'s interactive `sym =>` mode, `cbv at ...` hypothesis rewriting was removed.
- Unreachable code in `do` now warns instead of erroring; CI configurations that reject warnings may
  still turn this into a red build.
- Message-data visitors must handle the new `.ofOriginatingSyntax` constructor. Mathlib added this
  arm in its own message traversal code.
- Code relying on status emoji being stored in a trace header must stop stripping the emoji from the
  stored `MessageData`; rendering now adds it later.
- Uses of `Lean.RBMap` / `Lean.RBTree` should move to `Std.TreeMap` / `Std.TreeSet`; the old modules
  currently emit a deprecation warning rather than a hard error.
- `WPAdequate` was renamed to `WPSound` for code using `Std.Internal.Do` / `mvcgen` internals.

**Not observed in the first fleet port.** lean-gallery (26k lines, pure mathematics — combinatorics,
number theory, ordinal/proof theory, one ergodic-theory file) hit **none** of Part 1 A–F and none of
Part 2 G–L. That is a real datum about *shape*, not luck: every Part 1 entry is about `do`
notation, meta/parser code, `Std.Time`, or Lake linter selection, and a proof-only library contains
none of those. Expect the `do`-elaborator cluster to dominate ports of *tactic and tooling*
projects, and expect proof libraries to see mostly Part 2-style renames. Do not read a clean
proof-library port as evidence that the Part 1 entries are overstated.

# Part 4 — Build configuration and satellite pins (no source fix involved)

Sibling of the mature catalog's "Build-environment gotchas" group: things that make a bump fail (or
silently ship stale) with nothing wrong in any `.lean` file.

## N. `weak.warningAsError = true` re-shapes the entire error surface

**Evidence:** Fleet port (lean-gallery).

This catalog's premise is that *renames are self-documenting* — mathlib's `@[deprecated]` aliases
name their replacement, so they warn rather than break, and the expensive part of a bump is the
no-warning behavior changes. **That premise inverts in a repo built with warnings-as-errors.** There,
every deprecation alias mathlib adds in the window is a hard build failure, and the bump's error
surface becomes the *deprecation list* — the part the catalog treats as the easy case.

That is the setting working as designed, not a problem to route around: it is what stops a mature
repo from silently accumulating deprecation debt across bumps. Two practical consequences:

- **Read the errors before assuming a hard breakage.** A red build on a warnings-as-errors repo is
  most likely a one-line rename whose replacement is printed in the message. lean-gallery's entire
  v4.31 → v4.32 source delta was one such line (entry M).
- **A warm local tree will not show it.** `weak.` options are applied at build time and are not baked
  into oleans, so nothing in an already-built tree is invalidated by flipping the switch. Only a
  *fresh* build (or CI) enforces it — which is also why it is free to turn on at any time.

## O. Re-pin the satellites — the version lives in more than three files

**Evidence:** Fleet port (lean-gallery).

`lean-toolchain`, the lakefile's mathlib `rev`, and `lake-manifest.json` are the version sources in
the main build graph, so a stale one turns the build red immediately and you cannot miss it. A mature
repo records the version again in places `lake build` never reads, so missing one is green locally
and broken in CI — or, worse, publishes docs built against the old mathlib. The checklist:

| Satellite | Why it must move | Failure if missed |
|---|---|---|
| `docbuild/lean-toolchain` | the doc-gen4 sub-project runs on its own toolchain, deliberately outside the main build graph | docs job builds on the old Lean |
| `docbuild/lakefile.toml` → doc-gen4 `rev` | doc-gen4 is tagged in lockstep with Lean (`v4.32.0` exists) | doc-gen4 will not compile against the new toolchain |
| `docbuild/lake-manifest.json` | pins doc-gen4, doc-gen4's private deps, *and* the whole mathlib stack inherited through the path-require | manifest-out-of-date, or a doc build against mixed pins |
| CI `LEAN4EXPORT_TAG` | lean4export refuses oleans from a different Lean version (`incompatible header`) | comparator job fails after building four binaries |

**Regenerate the docbuild manifest with `lake update`, do not hand-write it.** Which pin wins for a
dep both sides declare (`Cli` is required by doc-gen4 at `main` *and* by mathlib at the release tag)
is lake's resolution order, not something to reproduce by hand — and a wrong guess only surfaces on
the docs job, which typically runs post-merge on the default branch. For the record, the v4.32
resolution kept `Cli` on mathlib's `v4.32.0` pin and moved `BibtexQuery` from `nightly-testing` to
`master`, following doc-gen4's own v4.32.0 manifest.

## P. Build every configured library, not just `defaultTargets`

**Evidence:** Fleet port (lean-gallery).

A repo can deliberately keep a `[[lean_lib]]` out of `defaultTargets` while CI still builds it —
lean-gallery's `Comparator` library is excluded because its challenge files carry `sorry` by design
(each sets `set_option warningAsError false`) and so must stay out of the main warnings-as-errors
build. A bump verified with `lake build` alone therefore calls the repo green while a configured
library is untested. Build the union of `defaultTargets` and every `[[lean_lib]]`.

The same asymmetry bites in the other direction: bare `lake build` in a repo that configures **no**
`defaultTargets` is a 0-job no-op — a silently vacuous green. Always name targets explicitly.
